# D01 — Rebuild Quoli's visual system, workspace UI/UX and landing page

Status: owner-requested design reset; **direction gate open**. Tracking: [QUO-82](https://linear.app/quolii/issue/QUO-82/d01-rebuild-quolis-visual-system-workspace-uiux-and-landing-page-from). Relative size: **L/XL**. Phase: cross-cutting design workstream before and alongside the hosted dashboard.

> Local scope record. Live status, comments and acceptance evidence belong in Linear. This file preserves reviewable scope and links the current direction gate.

## Owner assessment and why this exists

The current product and landing page read as generic, AI-generated design: default framework typography, undifferentiated card grids, decorative gradients, inconsistent spacing and hierarchy, weak product voice, and UI that looks assembled rather than designed. For a paid evidence product, that visual language undermines trust before a buyer reads a single claim.

This is not a polish pass. It is a deliberate reset of the brand, theme, visual system, core workspace UI, selected UX flows and the entire landing page. The direction is intentionally open at the start: the first deliverable is a small set of distinct directions for the owner to choose from, not a predetermined style.

## Direction gate

Do not implement a new theme until the owner chooses a direction. The current gate is recorded in [docs/design/directions/d01](../../design/directions/d01/README.md) with three complete visual worlds:

- **A — The Surveyor's Field Book** (lead proposal): territory, measured lines and deliberately blank ground.
- **B — The Phosphor Terminal**: the session as a transcript and the recorder as the interface.
- **C — The One-Bit Desktop**: a place with windows, folders and explicit unknowns.

Each direction includes a landing first viewport, a workspace shell, palette, typography, density, motion, rationale and honest risk, using the same synthetic session. The owner chooses one; the others are recorded as rejected. A re-roll and the conventional canon remain available.

## Objective

Deliver one coherent design system and apply it end to end:

1. **Brand and theme foundation** — typography, color, spacing, radii, elevation, borders, motion, iconography, illustration/imagery rules, light/dark behavior.
2. **Landing page** — positioning, narrative, hero, proof, product visuals, pricing/CTA, footer, responsive and accessible.
3. **Workspace shell** — navigation, project/workspace context, page headers, density, empty/loading/error states.
4. **Core screens** — sessions list, session review/timeline, evidence inspector, gaps, checks, captured changes, settings, cost, onboarding.
5. **Reusable components** — buttons, inputs, selects, tables, cards, badges, tabs, dialogs, drawers, tooltips, menus, pagination, toasts, data-viz primitives.
6. **Selected UX flows** — first run, connect a repository/harness, capture consent preview, review a session, drill into evidence, understand a cost estimate, recover from an error.
7. **Design documentation** — tokens and rules in code, a rewritten `apps/web/DESIGN.md`, updated design docs, and a component/state inventory.

## Scope detail

### Landing page

- Rewrite the narrative around the actual product: a local-first evidence recorder for coding agents, with a hosted dashboard as the target direction.
- Hero, product proof, how it works, evidence/privacy boundaries, supported harnesses, pricing/pilot CTA, FAQ, footer.
- Use only delivered capabilities or clearly label planned ones. Do not imply cloud sync, other harnesses, real prices or certifications that do not exist.
- Responsive from 320px up; keyboard accessible; reduced motion; no non-loopback requests; no fake social proof.

### Workspace

- Replace ad-hoc styles with tokens and shared components.
- Improve information hierarchy and density: session list, review/timeline, inspector, gap queue, checks, changes, settings.
- Make provenance, recorded/derived/inferred, partial/unpriced and gap states visually legible without reading a paragraph.
- Keep the existing evidence links, keyboard/list alternatives and local demo working.
- Add consistent empty, loading, error, disabled and permission states.

### UX flows

- First run: what Quoli is, what it captures, what it does not.
- Connect: detect supported harnesses/repos read-only, preview consent, show unsupported versions and recovery.
- Review: move from session to turn to tool/file/check/evidence without losing context.
- Cost: explain the formula, catalog version, partial/unpriced states and the difference between list price, reported cost and subscription.
- Errors: actionable recovery, no dead ends.

### Components and documentation

- Token source of truth (CSS variables or the existing token mechanism) and a component inventory.
- Every shared component documents states: default, hover, focus-visible, active, disabled, loading, empty, error.
- Rewrite `apps/web/DESIGN.md`; update `docs/design/session-workspace.md`, `landing-page.md`, `product-experience-review.md` and any screenshots that become stale.
- Add visual regression coverage for the landing page and key workspace screens.

## Non-goals

- No new backend, cloud, data-model, adapter or pricing capability.
- No framework migration or new UI dependency without demonstrated need.
- No marketing claims, legal copy or compliance badges without review.
- No dark patterns, fake urgency, fake testimonials, fake logos or invented metrics.
- No whole-repo rewrite; preserve evidence, capture, privacy and accessibility behavior.
- No hard block on backend/cloud work; UI-facing increments should coordinate with this direction.

## Acceptance criteria

- [ ] Owner approves one of 2–3 recorded design directions; the decision and rationale are in `docs/design/`.
- [ ] A token system covers type, color, spacing, radii, borders, elevation and motion; no page-level hard-coded values remain on redesigned routes.
- [ ] The landing page is fully rebuilt with real synthetic product visuals, responsive at 320/768/1024/1440, and contains no placeholder or fake content.
- [ ] The workspace shell and the listed core screens use the new system consistently.
- [ ] The shared component inventory documents all interaction states and keyboard behavior.
- [ ] Light/dark behavior (whichever the direction includes) meets WCAG AA contrast; focus is visible; reduced motion is respected.
- [ ] Five synthetic UX walkthroughs are completed and recorded: first run, connect, review, evidence drill-down, cost explanation.
- [ ] Playwright visual snapshots exist for the landing page and key screens at desktop and mobile; no horizontal overflow at 320px.
- [ ] Existing browser, accessibility/list-view, evidence-link, capture and privacy tests still pass.
- [ ] Copy is reviewed for truthfulness; every capability claim maps to delivered behavior or is explicitly labeled planned.
- [ ] `DESIGN.md` and the affected design docs are current; stale screenshots are replaced or removed.

## Test plan

- Manual design QA at 320, 768, 1024 and 1440 widths.
- Keyboard-only walkthrough of every redesigned flow; visible focus and logical order.
- Screen-reader smoke test of the landing page and session review (VoiceOver, NVDA or equivalent).
- 200% zoom and reduced-motion checks.
- Contrast measurement with a tool; record results.
- Playwright screenshots and the existing e2e suite.
- `pnpm typecheck`, `pnpm lint`, `pnpm test`.
- Synthetic fixtures only; no private sessions, credentials or paid APIs.
- Browser network assertion confirms no non-loopback requests.

## Privacy and security

- All screenshots, fixtures and demos use synthetic evidence.
- Do not present local-only data as uploaded or cloud-synced.
- Capture/upload consent copy must match the actual controls and defaults.
- Do not add fake trust badges, certifications, customer logos or security claims.
- Keep captured text inert; do not render untrusted HTML.

## Delivery increments

1. **Direction and foundation (M):** 2–3 directions, owner choice, tokens, type/color/spacing, `DESIGN.md` skeleton, landing page concept.
2. **Landing page (M):** full rebuild, responsive, accessible, real synthetic visuals, copy review.
3. **Workspace shell and core screens (L):** navigation, session list/review, inspector, gaps, checks, changes, settings, cost, onboarding.
4. **Components and UX states (M):** component inventory, states, keyboard behavior, empty/loading/error, visual regression.
5. **Validation and rollout (S/M):** accessibility, UX walkthroughs, screenshots, docs, cleanup of legacy styles.

Each increment gets its own PR and evidence. Do not merge a half-applied theme.

## Risks

- A redesign can break evidence links, keyboard navigation or the local demo; parity checks are required.
- Direction churn can stall delivery; the owner gate must produce one recorded choice.
- Marketing copy can overclaim; truthfulness review is mandatory.
- Visual work can drift into backend scope; keep this issue to design and front-end behavior.
- Screenshots can leak private data; use synthetic fixtures only.

## Open decisions for the owner

- Which of the proposed directions to take.
- Light only, dark only, or both.
- Brand voice: calm/technical vs bold/expressive.
- Landing CTA: pilot application, demo, waitlist or install.
- Keep the current information architecture or redesign navigation.
- Custom iconography/illustration vs a curated library.
- Which UX flows are must-have for the first redesign increment.

# V28 — Produce versioned signed release artifacts

Status: published to Quolii as [QUO-64](https://linear.app/quolii/issue/QUO-64/v28-produce-versioned-signed-release-artifacts); execution status lives in Linear. Relative size: **M**. Phase: **4 — Paid-pilot gates**.

## Vision alignment and user value

Advances **Commercial: distribution, CI and release discipline**. User value: produce versioned signed release artifacts so the developer can rely on the agreed evidence and product boundaries. Pillar definitions: [vision](../../vision.md).

## Scope and ownership

Suggested owner lane: **Release/packaging**. Bound implementation to this increment; enumerate touched callers, fixtures, config and documentation before coding.

Replace hard-coded local release versioning with the approved version source, reproducible inputs, signed manifests/artifacts, checksums and clear supported-platform metadata. Preserve the existing production bundle and artifact leak checks.

## Non-goals

Publishing credentials, an unsigned curl-to-shell installer or claiming byte reproducibility without measurement.

## Dependencies

V01, V05. These are local draft IDs. Replace with links to existing or newly published **Quolii** issues before starting; do not infer a dependency is complete because its code appears in the tree.

## Acceptance criteria

- A clean tagged build produces verifiable declared-platform artifacts; tampered artifacts fail verification; public release contents exclude private data.
- Record the demonstrated result, unsupported cases and validation evidence in the issue and relevant repository reference docs. Target capability alone does not satisfy acceptance.

## Test plan

Build twice under documented conditions, compare reproducibility boundaries and verify signatures/checksums with a temporary test key.

Run only meaningful checks for the final change, record actual outcomes and rerun regressions affected by shared contracts. A documentation/discovery task uses source, link and decision review rather than invented application tests.

## Privacy and security

Signing secrets stay out of repo/build logs; define public-key trust and key rotation.

Retain append-only provenance; unsupported values stay null or an explicit capability state. Captured text is inert untrusted data. Synthetic fixtures contain no real private sessions or credentials.

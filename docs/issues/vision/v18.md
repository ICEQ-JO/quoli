# V18 — Capture and inspect extension inventory versus invocation

Status: published to Quolii as [QUO-54](https://linear.app/quolii/issue/QUO-54/v18-capture-and-inspect-extension-inventory-versus-invocation); execution status lives in Linear. Relative size: **M**. Phase: **3 — Understanding**.

## Vision alignment and user value

Advances **P5**. User value: capture and inspect extension inventory versus invocation so the developer can rely on the agreed evidence and product boundaries. Pillar definitions: [vision](../../vision.md).

## Scope and ownership

Suggested owner lane: **Sources/extensions + experience**. Bound implementation to this increment; enumerate touched callers, fixtures, config and documentation before coding.

For the pilot harnesses, add consented read-only inventory and explicit invocation mappings for plugins, skills, MCP servers and commands. Record name/version/source/status where exposed and link invocation evidence to tools/prompts.

## Non-goals

Opaque plugin internals, effectiveness scores or broad filesystem crawling.

## Dependencies

V08, V10, V11, C12. These are local draft IDs. Replace with links to existing or newly published **Quolii** issues before starting; do not infer a dependency is complete because its code appears in the tree.

## Acceptance criteria

- Installed-only extensions are never labeled invoked; missing versions/status remain unknown; workspace opens invocation evidence or its declared gap.
- Record the demonstrated result, unsupported cases and validation evidence in the issue and relevant repository reference docs. Target capability alone does not satisfy acceptance.

## Test plan

Use adapter fixtures for installed-unused, invoked, failed, removed and opaque extensions; test content-disabled sessions and hostile names/URLs.

Run only meaningful checks for the final change, record actual outcomes and rerun regressions affected by shared contracts. A documentation/discovery task uses source, link and decision review rather than invented application tests.

## Privacy and security

Do not execute extensions to discover them; bound manifests and hide secrets in configs/server arguments.

Retain append-only provenance; unsupported values stay null or an explicit capability state. Captured text is inert untrusted data. Synthetic fixtures contain no real private sessions or credentials.

## Delivery

Select the concrete Quolii issue before implementation. Use an isolated branch/checkout and a PR that names this pillar/gate, final behavior, linked Linear issue, checks and material limits. Primary-agent review is required for supporting-agent output. No merge is authorized by this draft.

## Hosted delivery integration

The target surface is the authenticated Quoli cloud dashboard with paired local connectors. Local capture stays useful offline; upload needs separate category consent. UI work uses authorized cloud queries and tenant-scoped caches; source work emits the shared connector contract. Keep the synthetic/local demo working. Do not expose the loopback collector publicly. Architecture and debt work are concrete A-prefixed implementation issues, not an unspecified future product.

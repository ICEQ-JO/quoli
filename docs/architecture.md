# Architecture

Quoli is one small Node + React app. One process, one port, one SQLite file.

```text
Claude Code ──hook (stdin JSON)──▶ server/hook.mjs ──POST /ingest──▶ server/main.ts
                                                                     │
         transcript .jsonl (token usage) ◀──────── read incrementally┤
                                                                     ▼
                                                     ~/.quoli/quoli.db (SQLite)
                                                                     │
   repo on disk ──git / files──▶ code.ts · gitstate.ts · infra.ts    │
                                                                     ▼
                                 GET /api/* + /api/changes (poll) ──▶ web/ (React + React Flow)
```

## Data model

- **Events are the record.** Every hook payload is stored as received (after redaction), append-only. All views are derived from events at read time, so improving the derivation improves old sessions too.
- **Hooks follow the running server.** At startup the server rewrites Quoli's own hook entry in any project whose hooks are installed but point at another port or Quoli checkout. Other hooks and disconnected projects are left alone. Two Quoli servers sharing one data directory on different ports will keep taking the hooks from each other.
- **Tokens come from transcripts.** Claude Code hooks do not carry usage; each hook points at the session transcript, which records per-message usage. Messages repeat once per content block, so rows are keyed by message id and merged with `MAX`.
- **Derived sessions are cached in memory** per session and reused until that session gets a new event or usage row, the price table changes, or it is deleted. `live` is recomputed on every read because it depends on the clock. The cache starts empty on each server start.
- **Repository views are computed live** from the working tree (`git`, files on disk). They are not stored.
- **Costs and the report are derived, not stored.** Cost is computed per read from usage rows and the current price table, so editing prices re-prices history. Costs are estimates at list prices (no discounts, taxes, batch or long-context tiers), not invoices. Usage without a model id, or with a model matching no price row, is excluded and reported as unpriced.

## Security and privacy

- Binds to `127.0.0.1` only. Requests whose `Host` is not `127.0.0.1`/`localhost` are rejected (blocks DNS rebinding).
- **Local token and pairing (#10).** Quoli keeps a per-computer secret in `<QUOLI_HOME>/token` (owner-only, `server/token.ts`). Every `/api/` request must carry it in `X-Quoli-Token`, or gets `401 {pair: true}`; this covers Quoli's own page too, because any program or account on the computer can reach 127.0.0.1. Browsers get it once from a pairing link, `https://app.iceq.best/#pair=<token>` (or `http://127.0.0.1:<port>/#pair=` with `open --local`), which the CLI prints and `quoli open` opens. The fragment never reaches a server; `web/src/host.ts` stores it in `localStorage` and removes it from the address. `LocalGate` shows how to connect when Quoli answers 401. Hooks, the OpenCode plugin and the Pi extension seal every event with AES-256-GCM under a key derived from the token. `/ingest` refuses anything else, and a program that takes the port while Quoli is closed receives only ciphertext; a hook with no token, or one that is refused, queues the event instead. `POST /api/shutdown` needs the token as well. Limitations: a program running as the same account can still read the token file, which is no worse than it reading `~/.quoli` directly. A browser whose storage is cleared must be paired again.
- Every `POST`/`PUT`/`DELETE` under `/api/` requires `Content-Type: application/json` and an `Origin` of the server itself or of the Quoli app (`siteOrigins` in `server/app.ts`: only `https://app.iceq.best`), so other web pages, including the marketing site and account pages on iceq.best, cannot read sessions, change settings or delete data. `iceq.best/studio` redirects to app.iceq.best. app.iceq.best is served with a strict Content-Security-Policy (`vercel.json`: scripts only from the site plus the page's one inline script by hash, network only to the site and this computer, no framing); `tests/site-config.test.ts` fails if the inline script changes without its hash.
- Only those website origins get CORS headers on `/api/` (with `Access-Control-Allow-Private-Network` on preflights), so the full app on the website can read this computer's Quoli and no other site can read the answers. Trust boundary: a page served from the Quoli website can read local data; an XSS there would too, so the website keeps no third-party scripts. `/ingest` never gets CORS headers. Chrome and Edge ask the person before a public page reaches a loopback address (Local Network Access); Brave Shields and Safari may block it, and the page then points to `http://127.0.0.1:4400`.
- Connecting a project requires an absolute path that is a repository top level; hooks are written only to `<repo>/.claude/settings.local.json`. Project and retention deletion really delete rows, then truncate the WAL.
- `/ingest` requires `Content-Type: application/json`, which browsers cannot send cross-origin without a preflight Quoli never answers.
- File reads are limited to known project roots and paths inside them.
- Prompts, tool inputs and outputs are stored locally so the UI can show them. Common credential shapes (API keys, GitHub tokens, AWS keys, private keys) are redacted before storage; redaction is best-effort, not a guarantee. On macOS and Linux the data folder is owner-only (0700) and the database files 0600, tightened on every start (`makePrivate` in `server/db.ts`), so other accounts on a shared computer cannot read them; Windows keeps the user profile's access rules. `/api/file` resolves symlinks and refuses files whose real path is outside the project.
- Nothing is uploaded anywhere.

## Decisions

**2026-11 — Full rebuild.** The previous codebase (Next.js dashboard, collector, four adapters, three Git-host connectors, signed releases, ~150 docs) had broad scope but a UI the owner found unusable and no single clear workflow. It was removed and replaced by this smaller app built around one board with four lenses. The old code remains in git history (`git log` before the rebuild commit). Carried over as ideas, not code: the passive hook bridge, append-only events with derived views, and the recorded/derived/inferred distinction.

**2026-11-12 — Agent-neutral events (#116).** Other agents' hooks are mapped by an adapter into the shape Claude Code already sends, so derivation, the lenses and stored Claude Code history stay unchanged. Non-Claude events carry `quoli_agent` (and optionally `quoli_agent_version`); the absence of the field means Claude Code, so no migration was needed.

**Local content capture is on.** The old MVP defaulted to metadata-only, which made real sessions unreadable ("Content disabled" everywhere). The product's purpose is to show what the agent did, so prompts and tool I/O are stored locally with redaction. Cloud sync, when built, must be explicit opt-in per project.

## Known limitations

- Linux background service: when the user's systemd manager is stuck (jobs waiting forever), Quoli queues its jobs with `--no-block`, and if the service does not answer within 15 seconds it starts the same app copy as a detached process that runs until logout (#27), telling the person to run `systemctl --user daemon-reexec` or log in again so it starts at login. The queued job may still run once systemd recovers; it then finds the port taken and stops after its start limit. The unit has `ConditionPathExists` on its own files and a start limit (10 in 5 minutes), so deleting `~/.quoli` by hand no longer leaves it restarting forever.
- Collisions (#17) compare edits the agents reported and committed branch heads. Uncommitted work in two worktrees is compared by file only, not by conflict; edits made only through shell commands are not seen. Sessions on one branch that ran one after the other are not flagged. A branch that was merged and deleted can leave a collision showing until its sessions are a day old.
- macOS and Windows are tested in CI (GitHub runners, Node 22.13), not on people's own machines: Gatekeeper/SmartScreen prompts, antivirus that blocks the hidden Startup script, and Safari's or Brave's rules for a website reading this computer are unverified. On Windows the background Quoli starts at login, not when the machine boots.
- Review lens: Git attribution is by time and branch, not by author. Changes the user made during the session, and edits made only through shell commands (formatters, `sed`) appear when Git is used (they are marked `not in edits`) but a session with no recorded edit at all lists nothing. A session that never sent an end event (OpenCode, a closed terminal) counts commits up to 10 minutes after its last recorded activity, not up to now. Sessions whose branch is no longer checked out, or whose later commits cannot be separated, fall back to recorded edits. Function-level changes are not available yet. Reviewed marks are kept in this browser only.

- Code graph (#170) is syntactic, not a type checker: calls are tied only through imports, same-file names and `this`/`self`/receiver variables. Inherited methods, dynamic dispatch, re-assigned names, `import x = require()`, `export =`, workspace package names in monorepos and tsconfig `extends` are not followed, so such calls have no edge or only a `possible` one. Functions nested inside functions are not symbols (their calls belong to the enclosing symbol). Python `__all__` and Go build tags are ignored. Files over 512 KB, generated (`@generated`, `Code generated`, `DO NOT EDIT`), minified, `.d.ts` and anything under `node_modules`, `dist`, `build`, `vendor` are skipped, and at most 5,000 source files are read (`truncated`). Languages other than the five are only counted in `stack`.
- Claude Code, Codex, OpenCode and Pi can be connected. Codex specifics (contract: learn.chatgpt.com/docs/hooks and the generated schemas in `openai/codex` `codex-rs/hooks/schema`):
  - Codex runs project hooks only after the user trusts them with `/hooks` (or the project's `.codex/` layer is untrusted and nothing runs); until the first event the project shows Codex as waiting for trust.
  - Hosted tools such as WebSearch do not fire Codex hooks, so they are never recorded.
  - Codex has no tool-failure event. A result whose first lines report a non-zero exit (`Exit code: N`, `Process exited with code N`) is stored as a failure marked `quoli_failure_inferred`; other failures read as ok.
  - Token usage comes from `PostModelRequest.token_usage` per model request (`input_tokens` include cached input, so uncached input is stored as `input_tokens − cached_input_tokens`). Rollout files are not read.
  - A Codex subagent that runs under its own session id appears as a separate session.
- OpenCode specifics (OpenCode 2; plugin docs at opencode.ai/docs/plugins and opencode.ai/docs/build/plugins/server). The docs do not list event payloads, so the fields Quoli reads were observed with a logging plugin on OpenCode 2.0.32 in a scratch repository on 2026-11-12:
  - A plugin is a default-exported object `{ id, setup(ctx) }`; `ctx.location.directory` is the project, `ctx.app.version` the OpenCode version. Quoli's plugin never touches `ctx.credential` or OpenCode's database.
  - `ctx.tool.hook("execute.before" | "execute.after")` gives `sessionID`, call `id`, `tool` (`shell`, `read`, `write`, `edit`, `grep`, …), `agent` (the OpenCode agent, such as `build`), `input` (files are `path`, edits `oldString`/`newString`, shell `command`) and, after, `status` (`completed`/`error`), `result.output` (shell: `exit`, `output`) and `error.message`. A call fails when `status` is `error` or the shell exit is non-zero.
  - `ctx.session.hook("prompt")` gives the prompt text. `session.step.started` carries the model; `session.step.ended` carries per-step `tokens` (`input` uncached, `output`, `reasoning`, `cache.read/write`) and OpenCode's own `cost`. Quoli stores reasoning as output tokens and prices steps with its own table (OpenCode's cost is kept on the event, not shown). `session.execution.succeeded/failed` ends a turn. `session.text.ended` carries each finished text block in `data.text` (observed 2026-11-13); the plugin keeps the last one per session and sends it with the turn end as the agent's reply (#166).
  - OpenCode 2 runs one shared background service, so the plugin keeps only events for its own directory and sessions it has seen. There is no session-end event: an OpenCode session stops counting as live after ten quiet minutes.
  - Subagents run as child sessions and appear as separate sessions. Free or unlisted models (for example `minimax-m3.1-flash-free`) show as price unknown.
- Live prices (#143) are an estimate like the table: models.dev is community-maintained, a model without a cache price is charged its input price for cached tokens, and ids are matched as the agent reports them (exactly, as a dated snapshot, or without a `provider/` prefix), so a renamed id stays unpriced; a model only a reseller lists gets that reseller's price. With no price at all, totals show the token count instead of a cost (#162). A failed fetch keeps the previous prices and shows the error in Settings → Prices.
- User-level setup (#142). Each agent's user-level location is from its own docs: Claude Code user settings, Codex `~/.codex/hooks.json` (learn.chatgpt.com/docs/hooks: user hooks load in every project, trusted or not, but like any non-managed hook must be approved once in `/hooks`, and again whenever the hook command changes, for example after a port change), OpenCode global plugins in `~/.config/opencode/plugins/` (opencode.ai/docs/plugins), Pi global extensions in `~/.pi/agent/extensions/` (Pi docs/extensions.md). Limitations:
  - Verified with unit tests against a temporary HOME. Not yet observed with each agent loading the user-level file: OpenCode's `ctx.location.directory` for a global plugin is assumed to be the project directory, as it is for a project plugin.
  - Queued events are read only when the server starts. An event whose post timed out while Quoli was running waits for the next start and is then recorded after that session's newer events.
  - The queue stops growing at 50 MB. It holds hook payloads (prompts and tool output) on the local disk with owner-only permissions. The hook, plugin and extension redact them before writing, with the same rules as `server/ingest.ts` (`tests/local-files.test.ts` keeps the copies equal), so credentials never reach the disk even when redaction is turned off in Settings for live events.
  - Projects are still keyed by their local folder; `github` is a label and link. Two clones of one repository are two projects.
- Pi specifics (Pi 0.75; contract: the `docs/extensions.md` and `docs/session-format.md` shipped with `@earendil-works/pi-coding-agent`):
  - Pi auto-discovers project extensions in `.pi/extensions/*.ts` with no trust prompt. Quoli's extension uses `session_start`, `before_agent_start` (prompt), `tool_execution_start`/`_end` (`toolCallId`, `toolName`, `args`, `isError`, text of `result`), `message_end` (assistant messages: `model`, `usage.input/output/cacheRead/cacheWrite`), `agent_end` and `session_shutdown`. A shutdown for `reload` keeps the session open.
  - Tool inputs: `read`/`write`/`edit` take `path` (the adapter adds `file_path`), `edit` takes `edits[{oldText,newText}]` (one edit becomes `old_string`/`new_string`, several an `edits` list), `grep`/`find` take a folder `path` that is not treated as a file, `bash` takes `command`. Pi's own cost figure is not used; Quoli prices tokens with its own table.
  - Verified on 2026-11-12 by driving a real Pi 0.75.3 session through its SDK with the faux model provider (no credentials), which loaded the installed extension from the repository: prompt, a failing and a succeeding `bash`, an `edit`, and token usage were recorded. Not yet observed against a real model or a CLI quit, so `session_shutdown` from the CLI is untested.
- Sessions, usage, tool categories (`categorize` in `shared/model.ts`, lower-cased names for all three agents) and the Summary report are agent-neutral: they read Codex `apply_patch` bodies and argument-list commands and OpenCode's `oldString`/`newString` edits (its adapter maps OpenCode's `path` to `file_path`). The synthetic demo includes one Codex, one OpenCode and one Pi session in that shape. Codex and OpenCode sessions get token usage only from what their adapters report (no transcript reading), and a model without a price (for example `gpt-5-codex`) counts in tokens, not in spend. Prices match an exact model id or a dated snapshot of it (`<model>-<digit>…`), so `gpt-5` never prices `gpt-5.3-codex`. Built-in OpenAI prices are the standard tier up to 272K input; longer contexts, Batch, Flex and Fast mode cost differently and are not modelled.
- Hook payload fields were taken from Claude Code's documented hook contract and exercised with realistic synthetic payloads; verify against your installed version.
- Subagent ↔ spawning `Task` call is matched by launch order (drawn dashed), because hooks do not link them by id.
- Claude Code records some non-human turns as prompts. The Agents lens shows background-task notifications (`<task-notification>`) and slash commands (`<command-name>`) as one-line notices; other injected text still shows as a prompt.
- Map: calls come from the code graph (TS/JS, Python, Go); other languages show files without functions. A changed function is found by locating the recorded edit text in the current file, so edits made through Bash, Codex `apply_patch`, Write (whole file) or text changed again later are not marked at function level; the file still is. "Changed by this session" comes from recorded Edit/MultiEdit/Write calls; Git diff in the reader shows the rest.
- Infra is what config files declare, plus what the user adds by hand. Live status comes only from containers running in local Docker. Hosted providers (Vercel, AWS, Azure, Supabase and others) are listed when a file mentions them or the user adds a service there by hand, never as connected. A deploy command in a workflow (for example `gcloud run deploy`) adds an inferred deploy target when no file declares the host. Services added by hand are only what the user typed: Quoli never checks them and never fetches their dashboard links. Provider connections with live status and metrics are roadmap phase 4. What a pipeline deploys is inferred from its workflow steps, not from runs.
- Large repos: the code map lists up to 50,000 paths and reads line counts/imports for up to 5,000 files (≤ 512 KB); the Map explorer opens at package level. Git history pages 200 commits at a time (max 2,000 per request).
- Session lists show the newest 200 sessions per project (board sidebar) and 500 overall (Sessions, Home), and say so when older ones exist. Older sessions are kept, and the Git lens still attributes their commits.
- Transcripts are read in blocks of 8 MB. A single transcript line longer than that (a pasted image, a huge tool result) is skipped, so any usage on it is not counted.
- Per-prompt tokens and cost are attributed by time: each usage row (one model request or step) belongs to the prompt it falls after. Agents report usage per request, not per tool call, so Quoli never shows a cost per call. Time outside tool calls mixes model time and waiting for the user, so it is not labelled as either.
- Alerts run in the open Quoli tab only: no tab, no alert. They are evaluated when the overview refreshes (on each recorded event, every 30 seconds, and when a hidden tab is shown again), so a quiet alert can be up to about a minute late in a background tab. Settings and the record of fired alerts live in that browser's storage, so another browser starts fresh and may repeat an alert. "Ended" means the session left the live list: an end event, or 10 quiet minutes. A quiet threshold is therefore 1–9 minutes. The live "spend in the last 10 minutes" counts usage rows by their own time, so a long model request is counted when it finishes.
- Extensions (#135): MCP servers are named from `mcp__<server>__<tool>` (Claude Code and Codex, documented), preferring Claude Code's `mcp_server` field (v2.1.274+); a plugin is named only when Claude Code reports `source: "plugin"`, so older Claude Code versions show plugin servers by their scoped segment (`plugin_<plugin>_<server>`). Skills come from the `Skill` tool's `skill` input: the field is not in the published docs or SDK types and was read from Claude Code's own tool schema, so a rename would make skills disappear rather than be mislabelled. Skills typed as `/name` by the user bypass the tool and are not counted. Subagent types come from `subagent_type` on `Agent`/`Task`; a call without one shows as `default`. OpenCode names MCP tools `<server>_<tool>`, which cannot be split reliably, so they are not attributed.
- Insights reads sessions that started in the range and derives each one (cached per session), so a range with thousands of long sessions costs one derivation each on first load. A session counts on the day it started, even if it ran past midnight. The Sessions list a day links to shows at most the newest 500 sessions. Per-model figures use each session's main model, so a session that switched models counts once, under the model with the most tokens.
- Possible loops are inferred from fixed rules (`LOOP_RULES` in `server/loops.ts`): the same command failing 3 or more times, one file edited 5 or more times after a single prompt, an edit that exactly undoes an earlier one (only when the agent records old and new text, so not Codex patches), 4 or more failed calls in a row for one agent, and 10 or more reads and searches after a prompt with no edit or command. They are prompts to look, not verdicts: a loop can be legitimate (a flaky test retried on purpose), and loops the rules do not describe are missed. Thresholds are not configurable yet.
- Usage and budgets are estimates from transcript usage at list prices, bucketed by the server's local time zone. A budget is a display threshold, not an alert channel or a spending limit.
- The Git lens reads the local repository only. Remote branches are what the last `git fetch` saw, and commits that exist only on a remote are not drawn (the history follows local branches). A commit is tagged with a session only when that session's recorded `git commit` output printed its sha; `git commit -q` prints nothing, so such commits stay untagged.
- Themes: dark and light (System follows the OS). Contrast is enforced by `tests/theme-contrast.test.ts`; accessibility was checked with axe-core (0 violations on every page in both themes on the synthetic large demo at 1280 and 1600 px) and keyboard walkthroughs, not a real screen reader. `prefers-reduced-motion` turns motion off. The design system is recorded in DESIGN.md.
- Cost and the Summary report are heuristics: commands are classified from their text, line counts come from recorded Edit/MultiEdit/Write inputs (a Write's removed lines are unknown), failed edits are ignored, and only edits inside the project root are counted. Edits made through Bash (sed, formatters, generators) are not seen. The checklist lists things worth a look and never says the work is correct.
